# Prioritising Security-Critical Functions in the Linux Kernel (netfilter) with Graph Signals and LLM Reranking

NTU Final Year Project.

## Motivation

AI tools now find kernel bugs faster than developers can patch them. Developers
therefore need to know **where to look first**. This project ranks the functions of
the Linux kernel's **netfilter** subsystem by how security-critical they are, so the
most critical functions are reviewed and fixed first - without training a model,
using a lightweight *retrieve-then-rerank* design:

1. **Retrieve (cheap, structural):** build the netfilter call graph and combine five
   structural signals (PageRank, personalized PageRank from attacker entry points,
   betweenness from those entry points, function size, risky-operation count) with
   reciprocal rank fusion into a **shortlist** of K functions
   (after Gajjar et al. 2025, arXiv 2510.10321).
2. **Rerank (expensive, semantic):** a local LLM reviews only the shortlisted functions.
   The VulnSC-style reranker first summarises each function's callees bottom-up, then
   reviews the function with those summaries and a checklist; the score is computed
   from the model's findings (after Wu et al., ISSTA 2025).

Results: **[results/RESULTS.md](results/RESULTS.md)** (generated by the evaluation).
Earlier results on Linux 6.1.6 are kept unchanged in
[results/legacy_6.1.6/](results/legacy_6.1.6/RESULTS.md) for comparison.

## Pipeline

| Stage | Script | What it does |
|---|---|---|
| kernel | `analysis/setup/setup_kernel.py` | blobless + sparse git clone of Linux, check out the base tag |
| functions | `analysis/extraction/extract_all_functions.py` | every function in `net/netfilter` (incl. ipset templates), with size |
| calls | `analysis/extraction/extract_function_calls.py` | direct calls `foo(...)` |
| indirect | `analysis/extraction/extract_indirect_calls.py` | function-pointer calls matched by **struct type** (`c_types.py`), name-only fallback, API callbacks |
| seeds | `analysis/pagerank/build_seeds.py` | attacker entry points from `configs/seeds.yaml` |
| cves | `analysis/validation/build_cve_set.py` | CVE set: fix not in the base tag, bug in it; ground truth from `git show <fix>` |
| graphcheck | `analysis/extraction/graph_report.py` | old vs new call graph; is there a path seed -> buggy function? |
| shortlist | `analysis/shortlist/build_shortlist.py` | 5 signals + reciprocal rank fusion -> top-K shortlist |
| *(LLM, separate)* | `RUN_LLM_OVERNIGHT.bat` -> `run_llm_unattended.py` | LLM check (`llm_check.py`) and shortlist scoring (`score_shortlist.py`) with prompt v3 and VulnSC (`vulnsc.py`) |
| evaluate | `analysis/report/evaluate.py` | random / PageRank / PPR / combined / +v3 / +VulnSC; recall, top-N, MRR, bootstrap CIs, before/after July 2025 -> `results/RESULTS.md` |

Shared helpers: `analysis/config.py` (settings and paths), `analysis/callgraph.py`
(the call graph every script uses), `analysis/sources.py` (source files incl.
expanded ipset templates), `analysis/metrics.py` (rank, recall, MRR),
`analysis/llm/llm_client.py` (cached Ollama calls), `analysis/llm/jobs.py`
(resumable, time-capped LLM jobs).

Older scripts from the 6.1.6 study (`analysis/pagerank/calculate_pagerank.py`,
`evaluate_rankings.py`, `alpha_sensitivity.py`, `visualize_results.py`,
`analysis/fusion/`, `analysis/report/final_results.py`, `report_charts.py`,
`analysis/llm/tune_prompt.py`, `analysis/validation/collect_cves.py`, ...) are kept
for reference; they belong to the legacy results and are not part of the pipeline.

## Settings (all in `configs/`, no paths or secrets in the code)

| File | What it sets |
|---|---|
| `project.yaml` | kernel repository, clone folder (outside this repo), **base tag (v6.12)**, sparse paths, results folders, model release date |
| `cves.yaml` | CVE selection rules (30-40 CVEs, share of pre-July-2025 fixes, max functions per CVE) |
| `cve_split.yaml` | the tuning / test split - **written once, before any results** |
| `callgraph.yaml` | extra headers for struct types, API-callback rules |
| `seeds.yaml` | attacker entry points |
| `shortlist.yaml` | which signals, RRF k, **K = 150**, risky-operation list |
| `llm.yaml` | 3-hour cap per run, LLM check size (N = 150), VulnSC depth/size/scoring, fusion weights |
| `prompts.yaml` | prompt v1-v4 (v3 used for comparison) and the VulnSC prompts |
| `ollama.yaml` | model (`qwen3-coder:30b`) and Ollama address |

The base tag and its commit hash are written into every output file.

## Ground truth and fairness

- A CVE is used only if its bug is present in the base version: the fix commit is
  **not** in it (`git merge-base --is-ancestor <fix> v6.12` is false) and the commit
  named in its `Fixes:` line **is**.
- Ground truth = the functions the fix changes, mapped by name into the base version;
  anything that cannot be mapped is listed in `validation/cve_data_v6.12/summary.txt`.
- Leakage rule: a ground-truth function is never a seed (seeds are removed from the
  ground truth; the pipeline stops if one slips through).
- Settings (fusion weight w) are chosen on the **tuning** CVEs only; the **test**
  CVEs are used only for the final numbers. Each CVE is tagged as fixed before or
  after the model's release (July 2025).

## Setup

Requires Python 3.11, git, and [Ollama](https://ollama.com) with the model in
`configs/ollama.yaml` (`ollama pull qwen3-coder:30b`).

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe scripts\test_environment.py      # check the setup
# kernel CVE database (not in git, 500 MB):
git clone --depth 1 https://git.kernel.org/pub/scm/linux/security/vulns.git data/vulns
```

The kernel itself is downloaded by the first pipeline stage.
